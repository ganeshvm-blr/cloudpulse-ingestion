CloudPulse

Lightweight AWS-native observability system that transforms Lambda execution logs into structured metrics and computes latency percentiles (p50, p95, p99).

Problem

AWS Lambda logs are fragmented, unstructured, and distributed across multiple log streams. This makes it difficult to compute reliable system-level metrics such as latency distributions.

Solution

CloudPulse converts every Lambda invocation into a structured event that can be queried and analyzed deterministically.

Architecture (Event-Driven Pipeline)

Lambda Execution ↓ CloudWatch Logs ↓ Ingestion Lambda (log transformer) ↓ DynamoDB (CloudPulseEvents) ↓ Node.js CLI Analytics Engine ↓ p50 / p95 / p99 Computation

Core Design Principle

One Lambda invocation = One structured metric record

This removes log ambiguity and ensures deterministic observability.

Data Model (DynamoDB)

{
  pk: "SERVICE#lambda-name",
  sk: "TIME#timestamp#requestId",
  durationMs,
  billedMs,
  memoryMb,
  requestId,
  timestamp
}

What Makes This Important

  • Moves from log-based → event-based observability
  • Removes ambiguity in metric generation
  • Enables deterministic analytics
  • Aligns with real-world systems like Datadog & OpenTelemetry

Core Features

Event-driven ingestion Structured metrics CLI analytics engine Latency percentiles Serverless architecture

Tradeoffs

  • No real-time streaming layer (no Kinesis)
  • CLI instead of dashboards
  • Not optimized for high-scale production workloads

Scaling Plan

  • Add Kinesis ingestion buffer
  • Add pre-aggregation layer for metrics
  • Separate hot vs cold storage paths
  • Introduce visualization layer (Grafana / QuickSight)

CLI Usage

node cloudpulse-cli/index.js stats /aws/lambda/<function-name>
